# قاعدة البيانات (Supabase)

كل ملفات SQL في المشروع تُطبَّق **بالترتيب الزمني** (بادئة التاريخ في اسم الملف)، وهي موزعة على ثلاثة مجلدات:
`supabase/migrations` ثم `sql` ثم `db` — الترتيب الدقيق في **`db/MANIFEST.txt`**.

## التطبيق
```bash
DATABASE_URL="postgres://..." ./db/apply_all.sh      # من الصفر أو فوق قاعدة موجودة
```
أو الصق الملفات بالترتيب في Supabase → SQL Editor. كل الملفات **آمنة لإعادة التشغيل** (if not exists / create or replace / drop policy if exists) ولا تحذف بيانات.

## ملف الأساس
`db/20260810175000_baseline_reconstructed_tables.sql` يعيد بناء 8 جداول كان التطبيق يستعملها دون أن يكون لها ملف إنشاء
(`announcements, curriculum_subject_overrides, master_subjects, shared_subject_groups, shared_subject_members, site_settings, student_results, study_schedules`)
ودالة `cleanup_expired_push_subscriptions`. **على قاعدتك الحالية لا يفعل شيئاً** (ينشئ فقط ما هو غير موجود)؛ فائدته لبناء قاعدة جديدة من الصفر.
أعمدتها استُخرجت من استعمالها في الكود، فإن كان جدولك الحالي يحمل أعمدة إضافية فهي لا تتأثر.

## الاختبار
```bash
PGURL=postgres://postgres@localhost/postgres tests/db/run.sh
```
ينشئ قاعدة مؤقتة + مُحاكي Supabase (`tests/db/supabase_stub.sql`)، يطبّق كل الملفات مرتين (للتأكد من إعادة التشغيل)، ثم يشغّل `tests/db/checks.sql`
(منشورات/تعليقات/رسائل وصلاحيات التعديل، المراسلة بين التخصصات، البحث برقم التسجيل وحده، تثبيت وتمديد المشرف، سقف قائمة المشرف، إحصاءات الصفحة الرئيسية).

## اختبارات الأمان
`tests/db/security.sql` تُشغَّل تلقائياً بعد `checks.sql`: RLS على كل الجداول، جداول حساسة بلا صلاحية للزائر، قائمة الدوال العامة محددة بالاسم، كل دالة SECURITY DEFINER لها `search_path`، وسلوك فعلي كزائر مجهول ومستخدم عادي. أي دالة عامة جديدة تحتاج إضافتها عمداً إلى `expected_anon_fns`.

## قفل محاولات الدخول
`db/20261031090000_student_login_rate_limit.sql` يضيف قفلاً مؤقتاً بعد خمس محاولات اسم/رقم خاطئة. القفل مرتبط بجلسة المتصفح ورقم التسجيل معاً لمدة 15 دقيقة، ويُمسح عند نجاح التحقق، فلا يستطيع مهاجم حجب الطالب من جهاز آخر. يجب تطبيقه بعد `db/20261030090000_find_student_mask_name.sql`.

## بلاغ انتحال وحظر جهاز
`db/20261101090000_student_device_impersonation_reports.sql` يُطبّق بعد قفل الدخول. عند ظهور `device_in_use` يستطيع الطالب إرسال بلاغ مرتبط بجلسة الجهاز الأخرى النشطة. يراجعه المشرف من لوحة إدارة الطلاب؛ حظر البلاغ يُنهي جلسات الجهاز، يحذف اعتماده، ويمنع بصمته نهائياً من `student_gate` و`community_api`.

`db/20261102090000_registration_policy_report_status_unban.sql` يُطبّق بعده. يفرض أرقام التسجيل بالشكل `Ixxxxx` ابتداءً من `I18000`، ويضيف مفتاح `student_registration_enabled` الذي يتحكم به المشرف من لوحة الطلاب. يضيف حالة `unbanned` وسجل الحظر القابل للإلغاء، ودالة حالة البلاغ التي تعرض للطالب آخر نتيجة دون كشف بصمة الجهاز.

ملاحظة مهمة: المتصفح لا يملك صلاحية قراءة IMEI الحقيقي للهاتف. لذلك الحظر هنا يطبق على معرّف الجهاز السري المخزن في المتصفح وهاشه في قاعدة البيانات، وليس على IMEI عتادي. لا ينبغي وصفه للمستخدم على أنه حظر IMEI فعلي إلا بعد وجود تطبيق أصلي موثوق وموافقة صريحة.
